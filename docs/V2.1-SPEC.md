# v2.1 – nowy interfejs i funkcje „pełnego produktu” (specyfikacja)

Branch: `feature/ui-v2` we wszystkich trzech repozytoriach. Ten plik jest **kontraktem** między backendem,
frontendem i firmware dla wersji 2.1. Po scaleniu do `main` jego treść trafia do `PROTOCOL.md`, a etap jest opisany
w `ROADMAP.md` (etap 8).

Decyzje (2026-10-10):

- frontend: **Angular 22 + Angular Material 3** (Bootstrap i ng-bootstrap usunięte), Leaflet, Chart.js;
- cała aplikacja wymaga logowania; publiczne są tylko trasy udostępnione linkiem;
- role: `ADMIN` (wszystko), `VIEWER` (tylko odczyt + własne preferencje i hasło);
- breaking changes w API są dozwolone (frontend i backend zmieniają się razem).

### 2.1 Statystyki tras (`RouteStatsJob`)

- Ingest dalej aktualizuje na bieżąco `sample_count`, `started_at`, `ended_at` i dodatkowo ustawia `stats_dirty = true`
  (oraz `fix_count + 1` dla próbki z fixem).
- `@Scheduled(fixedDelay = 30 s)`: dla każdej trasy z `stats_dirty` (max 50 na przebieg) jednym zapytaniem SQL
  przelicza wszystko od zera i ustawia `stats_dirty = false`. Także po usunięciu punktu i po imporcie.
- Definicje:
  - `min/avg/max_usv` – po wszystkich próbkach;
  - `dose_usv` = Σ `usv_i × min(ts_i − ts_{i−1}, 60 s) / 3600` (przerwy > 60 s nie są całkowane; pierwsza próbka = 0);
  - `distance_m` = Σ haversine między kolejnymi próbkami **z fixem**, pomijając odcinki z prędkością > 100 m/s
    (skoki GPS); NULL gdy < 2 punktów z fixem;
  - `preview.track` – maks. 150 punktów z fixem (co k-ty + ostatni), `[lat, lon, usv]`, lat/lon zaokrąglone do 5 miejsc,
    usv do 3;
  - `preview.spark` – 60 wartości: `ntile(60)` po czasie, max(usv) w kubełku (mniej, gdy próbek < 60).
- Migracja oznacza wszystkie istniejące trasy jako `stats_dirty`, więc dane z pracy przeliczą się po starcie.

RouteDto {
  id, deviceId, deviceName, deviceRouteNo, name, description,

  sampleCount, fixCount,

MeasurementDto, MarkerDto – bez zmian względem v2.0.

### 3.3 Urządzenia

| Metoda i ścieżka | Opis |
|---|---|
| `GET /api/devices` | `DeviceDto[]` |
| `GET /api/devices/{id}` | `DeviceDto` |
| `PATCH /api/devices/{id}` | `{name}` |
| `POST /api/devices/{id}/commands` | `{cmd: "new-route"\|"battery"}` → 202; dodatkowo zdarzenie `COMMAND_SENT` |
| `GET /api/devices/{id}/health?from&to` | `HealthPoint[]` rosnąco (domyślnie ostatnie 7 dni, max 5000 punktów) |
| `POST /api/devices/{id}/import` | multipart, pole `files` (1–20 plików `.jsonl`/`.txt`, łącznie ≤ 50 MB) → `ImportResult` |

```text
DeviceDto   { id, name, online, lastSeenAt, fwVersion, currentRouteNo, currentRouteId, lastReset,
              batteryMv, batteryPct, batteryAt, signalCsq, signalAt, routeCount }
HealthPoint { ts, batteryMv, batteryPct, signalCsq }
ImportResult { files, lines, imported, duplicates, invalid,
               routes: [{ routeId, deviceRouteNo, imported }] }
```

Import: każda linia = ramka telemetrii v1 (to samo co MQTT). Linia bez poprawnego `ts` → `invalid` (przy imporcie nie ma
sensownego czasu serwera). Zapis tym samym `INSERT ... ON CONFLICT DO NOTHING` co MQTT → linie już odebrane na żywo to
`duplicates`. Po imporcie: trasy `stats_dirty`, zdarzenie `IMPORT`.

### 3.4 Zdarzenia i alerty

| Metoda i ścieżka | Opis |
|---|---|
| `GET /api/events?deviceId&type&page&size` | `Page<EventDto>`, od najnowszych |
| `GET /api/alerts?state=open\|all&page&size` | `Page<AlertDto>`, od najnowszych (domyślnie `all`) |
| `GET /api/alerts/count` | `{open}` |
| `POST /api/alerts/{id}/ack` | `AlertDto` |
| `POST /api/alerts/ack-all` | `{acknowledged}` |
| `GET /api/alert-rules` | `AlertRuleDto[]` |
| `POST /api/alert-rules`, `PUT /api/alert-rules/{id}` | body = `AlertRuleDto` bez `id` → `AlertRuleDto` |
| `DELETE /api/alert-rules/{id}` | 204 |

```text
EventDto     { id, deviceId, deviceName, routeId, ts, type, severity, message }
             type: DEVICE_ONLINE | DEVICE_OFFLINE | ROUTE_STARTED | BATTERY | DEVICE_ERROR | MARKER |
                   COMMAND_SENT | ALERT | IMPORT
AlertDto     { id, ruleId, ruleName, type, deviceId, deviceName, routeId, ts, value, threshold,
               latitude, longitude, message, acknowledgedAt, acknowledgedBy }
AlertRuleDto { id, name, type, threshold, deviceId, enabled, cooldownMinutes, notifyPush }
```

Ocena reguł (backend):

- `DOSE_RATE_ABOVE` – po zapisaniu każdej próbki: `usv >= threshold`;
- `BATTERY_BELOW` – po statusie / zdarzeniu `battery`: `pct < threshold`;
- `DEVICE_OFFLINE` – po `{"online":false}` (Last Will).
- Reguła z `deviceId = null` dotyczy wszystkich urządzeń. Nie więcej niż 1 alert na (reguła, urządzenie) w `cooldownMinutes`.
- Reguły trzymane w pamięci (przeładowanie po każdej zmianie), żeby nie odpytywać bazy przy każdej próbce.
- Alert → wiersz `alerts` + zdarzenie `ALERT` (severity `WARN`) + SSE `alert` + push ntfy (gdy skonfigurowany
  i `notifyPush`), asynchronicznie – nigdy nie blokuje zapisu próbek.

Push przez [ntfy](https://ntfy.sh): `POST {app.notify.ntfy.url}` (np. `https://ntfy.sh/<losowy-temat>`), treść = `message`,
nagłówki `Title`, `Priority` (`high` dla dawki, `default` dla reszty), `Tags` (`warning`), `Click`
(`{app.public-url}/alerts`), opcjonalnie `Authorization: Bearer {app.notify.ntfy.token}`. Klient HTTP z JDK.

### 3.5 Statystyki, mapa zbiorcza, wyszukiwanie

| Metoda i ścieżka | Odpowiedź |
|---|---|
| `GET /api/stats/summary` | `{routeCount, deviceCount, devicesOnline, sampleCount, distanceM, doseUsv, maxUsv: {value, routeId, routeName, ts} \| null, openAlerts, lastRoute: RouteDto \| null}` |

| `GET /api/search?q` (min. 2 znaki) | `{routes: [{id, name, deviceId, startedAt}] (≤8), devices: [{id, name}] (≤5), markers: [{id, routeId, label, ts}] (≤5)}` |

### 3.6 Live – Server-Sent Events `GET /api/stream`

`text/event-stream`, wymaga sesji. Co 20 s komentarz `: ping`. Timeout połączenia 30 min (EventSource sam się łączy
ponownie; frontend po ponownym połączeniu dociąga brakujące próbki przez `?after=`).

| `event:` | `data:` |
|---|---|
| `measurement` | `{routeId, deviceId, measurement: MeasurementDto}` |
| `route` | `RouteDto` bez `preview` – nowa trasa i po przeliczeniu statystyk |
| `device` | `DeviceDto` – zmiana online / baterii / trasy |
| `alert` | `AlertDto` |
| `event` | `EventDto` |

Wysyłka po commicie transakcji (`@TransactionalEventListener(AFTER_COMMIT)`), osobnym wątkiem; wolny klient nie
blokuje ingestu. Maks. 50 jednoczesnych połączeń.

## 4. MQTT – zmiany v2.1 (zgodne wstecz, nadal `v: 1`)

- `status` dostaje pole `csq` (0–31; 99 = nieznany → nie wysyłać): `{"online":true,"fw":"2.1.0","r":42,"reset":"POWERON","bat_mv":3980,"bat_pct":70,"csq":18}`.
- Firmware co `HEALTH_INTERVAL` (10 min) wysyła zdarzenie `{"type":"battery","mv":3950,"pct":66,"csq":17}`.
- Backend: każdy odczyt baterii / zasięgu → wiersz `device_health` + aktualizacja `devices` + ocena `BATTERY_BELOW`.
